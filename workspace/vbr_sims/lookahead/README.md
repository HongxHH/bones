# 档案：多段前瞻 MPC、增量传输+渐进增强、帧级DP联合（lookahead）

- 状态：已封板（仿真器 oracle 级证据；2026-08-29 实验，2026-10-10 复核）
- 时间：实验 2026-08-29（commit 432d645）；复核 2026-10-10
- 最近复核：2026-10-10（7 runner 全读、control 三器全读、4 个结果 json 现算/重跑比对、陈旧单轨迹 json 已替换）

叙事文档：`docs/exploration_log.md` 阶段 8。控制器代码不在本目录，在仓库根 `control/`。

## 1. 要回答的问题

三组相互关联的仿真器问题：

1. **多段前瞻 MPC**：BONES 逐段贪心选（码率 d，增强档 e）。若滚动时域枚举未来 N 段的
   (d,e) 序列、只执行第一段（receding horizon），能否靠前瞻减少误判与振荡？
2. **增量传输+渐进增强**：段下载完即以基础质量可播，GPU 利用缓冲提前量在后台优先增强
   高增益帧，播放时未增强帧用基础质量——能否救回"整段来不及增强"的段？
3. **帧级 DP 与增量联合**：在 2 的框架内再用逐帧背包 DP 分配每帧增强级别，能否叠加收益？

## 2. 方法概述

- 前瞻：`control/bones_ca.py:338-442` `_lookahead_control`。枚举
  product(5 码率 × 4 增强档)^N（N=2 为 400、N=3 为 8000 序列/决策点），对每条序列做
  简化双缓冲连续速率仿真（下载期增强以 seg_time/en_time 速率从下载缓冲搬到增强缓冲、
  播放 1:1 消费、不足记 freeze），目标=Σ(漂移−V·奖励)/段大小 + 手写 freeze 惩罚，
  只执行 best_first。未来带宽假设恒定=当前 EWMA；未来段大小取 manifest（合理）。
- 增量：`control/bones_incremental.py`（291 行）。下载收尾时按缓冲水位+seg_time/2
  估算可增强帧数，用逐帧真实增益 argsort 选 top-k 帧以 BONES 所定 max_level 增强，
  段 VMAF=已增强帧增强质量与其余帧基础质量的逐帧平均，增强缓冲只按已增强帧数计费。
- 联合：`control/bones_combined.py`（334 行）。先在整段增强时间预算内做逐帧 4 级
  背包 DP（10ms 时间网格）得每帧理想级别，再按理想增益排序在可用时间内挑帧。
- 数据：BBB 30fps、120 帧/段；前瞻多轨迹用真实 3G/4G/hd 轨迹（0913/0914/0921 等），
  三/四方案对比用 4 条**手工合成** 30s 阶梯带宽轨迹（`data/trace/{3g_low,4g_medium,
  wifi_high,volatile}.json`，2026-08-29 生成）。

## 8. 是否重做：判断与方案

**三条线均不原样重做，封板；有效科学问题并入帧级调度复活簇（帧级指标体系 A/B 阶段之后）。**

- 前瞻 MPC 的因果版**以可用的逐帧/逐段增益预测器为前提**，而 #4 已证预测器时序
  外排 R² 为负——在预测器过关前重跑前瞻只会重复上界数字。复活顺序：先 A（统一
  连续测量管道重测帧级质量）→ B（walk-forward 预测器，只看 Spearman/TopK）→
  再做因果前瞻，且内部卡顿模型必须换成秒单位逐事件口径（L2）、用真实轨迹。
- 增量/联合若复活，必须同时改四点：① 删除整段可行性闸门、建跨段全局 GPU 工作
  队列（I1/J2）；② 去掉 seg_time/2 赠送，时间预算由队列仿真给出（I2/J3）；
  ③ 选帧改因果预测排序（I3/J4）；④ 成本连续毫秒记账、决策与记账同一套数（J1）。
  该机制与 #2 帧级 DP 是同一科学问题的两个壳，复活时合并为一条线，不另立。
  I1/I2/I3/J1/J2/J10 的逐行改法、顺序与验收统一见 `docs/frame_scheduling_fix_plan.md`（M0-M5，2026-10-10 现地核码），以该清单为准。
- **M1/M2 已完成（2026-10-10）**：`bones_combined.py` 的 DP 已切到 `simulation/gpu_grid.py` 0.1ms 网格（J1：删除 +1 向上取整与 5000 步硬帽），缓冲推入改用决策网格成本之和并带 ≤6ms 残差断言（J10）；`bones_incremental.py` 帧数计算与推入同步网格同源。three_way/four_way 四轨迹冒烟通过。I1/J2 闸门与 I2/J3 的 seg_time/2 赠送仍在（M3/M4 处理），I3/J4 oracle 选帧仍在（M5 处理）。
- "增量传输"若未来指真实 SVC/残差字节，属于 #15 side_channel 范畴（已 NO-GO），
  本目录的同名仿真器不传递任何额外字节，禁止混为一谈（I8）。

## 9. 踩坑铁律

- 仿真器里任何"未来段质量"都必须标注 oracle；滚动时域的价值必须用
  N2−N1（同 oracle 口径）隔离，不能与 BONES 静态表直接相减后归给前瞻。
- 复用 BONES 闸门时逐行检查：号称"绕过整段可行性"的机制若保留原闸门，机制不触发。
- 背包 DP 的时间网格取整方向（向上/向下）都会扭曲档位相对成本；决策与记账必须
  用同一套成本值。
- 仿真器 QoE 卡顿是 ms/10 口径（#6 C1b），绝对 QoE 不与播放器混用。
- 批量 runner 跑完后必须用当前代码重跑校验归档 json；修单位 bug 的同一 commit
  最容易夹带修复前产物（L5 教训）。
- 移动脚本目录后 sys.path/相对路径要随迁或统一用 PYTHONPATH（L10）。
- 合成阶梯轨迹只配做机制冒烟，不配做效果结论。
