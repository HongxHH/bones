## 0. 我们的方法叫什么（工作名）

1. **多类型工具表**（低清 SR + 高清同分辨率增强等）

## 3. 各臂实现要点（工程）

### 3.1 `ours` / `none` / `fixed_high`

与 D3 相同；脚本可复用 `scripts/run_d3.py` 思路，扩展为 `scripts/run_d5.py`。

### 3.2 `no_hd`

**推荐（少改代码）：** 运行前加载 quality 后把

- `Q[3, TOOL_SR_X2_MED]`、`Q[3, TOOL_RESTORE_SHARP]`  
- `Q[4, TOOL_RESTORE_SHARP]`  

置为 −inf（或 CLI/`tool_mask=no_hd`）。LEGAL 可不动——策略因 Q 不可选。  
延迟表可保持，避免无关键变量。

### 3.3 `no_slack`

在 `tool_greedy._pick_tool` 增加开关（如 `config.tool_ignore_slack=true`）：

- 仍尊重 `LEGAL_BY_DOWNLOAD` 与 `Q` 有限  
- **跳过** `slack_ms < t_ms` 与（可选）`t_ms >= seg_time` 两道门  

这样消融的是「缓冲/截止约束」，不是「合法工具」或「质量表」。

### 3.4 `no_fc`

仅 `--use_fast_complete false`；其余与 ours 相同。

### 3.5 公平性纪律（必守）

1. 同一内容上，**所有臂共享同一套校准 Q 表口径**（D4 教训：旧 tos 表虚高会毁对照）。  
2. QoE 目前为查表；论文写明局限；D5 不阻塞在全片真 VMAF。  
3. 记录 `tool_or_level_hist`、`download_action` 分布、stall、fast_complete 段数。

## 4. 1080 闭环（RQ1，与消融并行或紧前）

### 4.1 探针

- 输入：TOS/BBB 的 **native 显示分辨率**（BBB 1920×1080；TOS 1920×800）  
- 臂：`identity/bicubic` vs `restore_sharp`（当前 USM 占位）  
- 样本：≥5～10 内容段（避开片头）  
- **GO：** 相对 identity 均 ΔVMAF ≥ +1.0 → 写入对应行 `Q[4, restore]`  
- **NO-GO：** 不入表；`RESEARCH`/论文改口为「高清增强以 720 档工具为主，1080 保持 none」

## 6. 判决标准（门禁）

### 主消融表（相对 ours）

| 期望 | 含义 |
|---|---|
| ours ≫ none | 系统整体有用（已有 D3/D4，D5 复现） |
| ours 不显著差于 fixed_high，或 stall 明显更好 | 「会选」不劣于蛮干 |
| ours > no_hd（QOE 或高清段质量/占用） | 高清多类型有贡献 |
| ours 优于 no_slack（尤其 stall，或同等 VMAF 更稳） | 缓冲可行集有贡献 |
| ours 优于 no_fc（stall 更少，或同等 stall 下浪费更少） | fast-complete 有贡献 |

若某一消融「差不多」：如实写 **该组件在该轨迹上增益有限**，不要删臂；换 0921/TOS 再看是否轨迹依赖。
