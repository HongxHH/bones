# 服务端联合优化仿真架构设计

## 1. 核心思想

当前BONES是**纯客户端决策**：
- 客户端独立估计带宽、管理缓冲区、选择码率和增强级别
- 服务端只负责存储和传输码流，不参与决策
- 多客户端共享瓶颈链路时，各自为政，导致全局次优（如同时冲高码率导致拥塞）

**服务端联合优化**：服务端掌握全局信息，联合优化多客户端的码率选择、增强决策和带宽分配：

```
客户端1 ↘
客户端2 → 服务端（全局优化器）→ 联合决策 → 各客户端执行
客户端3 ↗
```

**本地仿真**：由于我们只有单机环境，在本地实现一个"虚拟服务端"进程，模拟多客户端场景下的联合优化。

## 2. 问题建模

### 2.1 多客户端联合优化

**系统状态**：
- 对每个客户端$i$：缓冲区$B_i$、带宽估计$\hat{C}_i$、内容特征$X_i$、GPU能力$G_i$
- 全局：瓶颈链路总带宽$C_{\text{total}}$、服务器负载$L$

**决策变量**：
- 对每个客户端$i$：码率$r_i$、增强级别$a_i$（或帧级增强数组）
- 全局：带宽分配$\{c_i\}$，满足$\sum c_i \leq C_{\text{total}}$

**目标函数**：
$$\max_{\{r_i, a_i, c_i\}} \sum_i w_i \cdot \text{QoE}_i(r_i, a_i) - \alpha \cdot \text{fairness\_penalty} - \beta \cdot \text{server\_load}$$

其中：
- $\text{QoE}_i = \text{VMAF}_i - \lambda \cdot \text{stall}_i - \mu \cdot \text{quality\_switch}_i$
- $w_i$：客户端权重（可设为相等，或按优先级）
- fairness_penalty：$\sum_i |\text{QoE}_i - \overline{\text{QoE}}|$（保证公平性）

### 2.2 服务端增强感知

服务端知道每个客户端的GPU能力和当前负载，可以：
- 对GPU弱的客户端：分配低码率（减少增强需求）或推送预增强数据
- 对GPU强的客户端：分配高码率+高增强（充分利用端侧能力）
- 全局均衡：避免所有客户端同时选择高增强导致服务器推流压力

### 2.3 服务端内容预计算

服务端预计算所有视频的内容特征（运动、纹理、场景切换）：
- 客户端请求时，服务端将该段的内容特征一并下发（120帧×少量字节）
- 客户端无需自行提取特征，减少端侧计算开销
- 服务端可基于内容特征做更精准的码率标注（VBR而非CBR）

        self.algorithm = algorithm  # "wfq" (加权公平), "drr" (赤字轮询), "fixed" (固定比例)

## 4. 仿真流程

### 4.1 单轮仿真

```
初始化:
  - 创建服务端 (总带宽=10Mbps, 客户端数=3)
  - 创建3个客户端 (不同轨迹+GPU能力)
  - 加载视频内容特征库

循环 (每个时间步=100ms):
  for each client:
    1. 更新本地状态 (播放进度, 缓冲区, 带宽估计)
    2. 如果需要下载新段, 向服务端请求决策
    3. 服务端全局优化, 返回码率+增强+带宽分配
    4. 客户端按分配带宽下载, 按增强级别增强
    5. 统计QoE指标

结束:
  - 汇总各客户端QoE
  - 计算公平性指数 (Jain's Fairness Index)
  - 对比基线 (各客户端独立BONES决策)
```

### 4.2 实验场景

| 场景 | 客户端数 | 轨迹组合 | 总带宽 | 研究问题 |
|------|---------|---------|--------|---------|
| S1: 同质客户端 | 3 | 3×4G | 15Mbps | 联合优化vs独立决策的增益 |
| S2: 异质带宽 | 3 | 3G+4G+WiFi | 10Mbps | 服务端如何公平分配 |
| S3: 异质GPU | 3 | 3×4G | 15Mbps | 服务端感知GPU能力的优化 |
| S4: 拥塞场景 | 5 | 5×4G | 10Mbps | 高负载下联合优化的优势 |
| S5: 内容异质 | 3 | 3×4G | 15Mbps | 不同内容(运动/静态)的联合优化 |

### 4.3 对比基线

1. **独立BONES**：每个客户端独立运行BONES，TCP公平共享带宽（当前状态）
2. **服务端固定比例**：服务端按固定比例分配带宽，客户端仍独立决策
3. **服务端联合码率**：服务端联合优化码率选择，但增强决策仍在客户端
4. **服务端全联合**：服务端联合优化码率+增强+带宽分配（我们的方案）

## 5. 关键指标

### 5.1 QoE指标
- 各客户端平均VMAF
- 各客户端卡顿时间
- 各客户端质量切换次数
- 加权平均QoE（$\sum w_i \cdot \text{QoE}_i$）

### 5.2 公平性指标
- Jain's Fairness Index：$J = (\sum \text{QoE}_i)^2 / (n \cdot \sum \text{QoE}_i^2)$
- QoE方差：$\text{Var}(\text{QoE}_i)$
- 最差客户端QoE：$\min_i \text{QoE}_i$

### 5.3 效率指标
- 带宽利用率：实际使用带宽/总带宽
- GPU利用率：各客户端GPU使用情况
- 服务端决策延迟：全局优化的计算时间

## 6. 与纯客户端BONES的对比

| 维度 | 纯客户端BONES | 服务端联合优化 |
|------|--------------|---------------|
| 决策信息 | 局部（仅自身状态） | 全局（所有客户端+网络） |
| 带宽分配 | TCP拥塞控制（被动） | 显式分配（主动） |
| 多客户端公平性 | 不保证（TCP公平≠QoE公平） | 显式优化 |
| 内容感知 | 客户端自行提取 | 服务端预计算下发 |
| 增强决策 | 客户端独立 | 服务端联合（感知全局GPU资源） |
| 可扩展性 | 好（无中心节点） | 中（服务端为瓶颈） |
| 部署复杂度 | 低 | 高（需服务端改造） |
| 仿真可行性 | 已有 | 本地可仿真 |

## 7. 实现路线

### 阶段1：单客户端服务端化（验证接口）
- 将现有BONES的决策逻辑移到"服务端"
- 客户端只负责执行，不做决策
- 验证QoE与原BONES一致（无联合优化增益，因为只有1个客户端）

### 阶段2：多客户端独立决策（基线）
- 启动3个客户端，各自向服务端请求决策
- 服务端不做联合优化，只转发各客户端的独立BONES决策
- 带宽用TCP公平共享模拟
- 建立基线数据

### 阶段3：联合带宽分配
- 服务端用WFQ/DRR显式分配带宽
- 对比TCP公平共享的差异
- 验证带宽分配的公平性和效率

### 阶段4：联合码率+增强决策
- 服务端全局优化码率和增强选择
- 对比独立决策的QoE和公平性
- 多场景测试

### 阶段5：内容感知+帧级调度
- 服务端预计算内容特征，下发给客户端
- 联合帧级增强调度
- 完整方案验证

## 8. 风险与缓解

| 风险 | 影响 | 缓解 |
|------|------|------|
| 全局优化计算复杂 | 决策延迟高 | 小规模穷举+交替优化，控制客户端数<5 |

| 服务端单点故障 | 系统不可用 | 仿真中不考虑，论文中讨论分布式扩展 |
| 与现有播放器集成难 | 无法实测 | 先在仿真器中验证，播放器集成为可选 |

## 10. 单客户端"服务端增益引导"的证伪结论（2026-09-06，阶段16）

本节是上述多客户端联合优化之外的另一条服务端协同分支——**不下发带宽/码率决策，只下发服务端用原始无损帧算出的近 Oracle 增强增益图谱，客户端码率层冻结、增强层独立非阻塞执行**。该分支已用纯仿真快速证伪，记录在此避免重复投入。

### 10.1 与第 1~9 节的区别

- 第 1~9 节：多客户端共享瓶颈链路时的全局码率/带宽/公平性联合优化（未实现）。
- 本节：单客户端下，服务端内容认知能否指导"每段用哪级增强、增强谁、什么顺序"。脚本 `workspace/gain_predictor/step22_server_guided.py`。

### 10.2 实验设置

码率下载序列与卡顿完全冻结为原 BONES（三线相同），增强层为独立非阻塞 GPU 轨道：段在下载完成时刻可用、播放时刻为截止期，仅当 `t+enhance_time≤play_i` 才启动，来不及即跳过，永不阻塞播放、永不反压码率。调度统一 EDF 保序。130 轨迹 × GPU 倍率 {1.0,0.6,0.4,0.25}。播放时间线由下载完成时刻递归重建，逐段卡顿重建值与仿真器 `idle_time` 误差恒为 0。

### 10.3 结论：服务端增益图谱无决策空间

1. **选哪级方法——真值零增量**：`oracle 选真值增益最高` 相对 `选最强可行级别`（不看真值）ΔQoE≈0.000、胜率 3%~18%。SR 增益对级别单调，客户端直接选最强即可，服务端下发"该用哪级"无价值。
2. **增强顺序——乱序有害**：按增益/效率乱序违反 EDF 可调度性最优，会让早播放段错过窗口，不如段序。
3. **稀缺时跨段分配——内容真值改不了物理窗口**：段能否增强由下载-播放时间窗客观决定；GPU 紧张时非阻塞贪心多增强反而在相邻段产生"增强/不增强"跳变，振荡 +2.2 吃掉 VMAF 增益（ΔQoE −1.7）；本地级别平滑也无法消除（主因是窗口碎片化而非级别跳变）。
4. 唯一正向项是"非阻塞执行吃满播放前窗口"：GPU 充足时 +1.55 QoE/胜率 98.5%，但多花 42% GPU、且不依赖任何服务端内容认知，纯本地规则即可获得；GPU 一慢即转负。

### 10.4 对本文件原规划的影响

- "服务端内容特征/增益下发指导客户端增强选择"（对应 2.3、阶段5）在当前超分单任务 + 段级平均 VMAF 设定下不成立，不投入实现。
- 仍未排除、与本节不冲突的方向：① 多客户端带宽/公平性联合（1~9 节，问题不同）；② 异构增强（去块/去噪/插帧/HDR）间非单调选择；③ 帧级/最差分位质量口径；④ 服务端直接下发预增强结果（计算下沉/边缘转码），而非下发引导信令。这些是独立问题，需另做证伪。
