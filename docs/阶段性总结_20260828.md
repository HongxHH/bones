# 阶段性总结：神经增强视频流系统研究

**时间范围**：2026-08 前期 ~ 2026-08-28
**当前分支**：dev/experiments

---

## 一、项目背景与目标

基于 BONES（2024 SIGCOMM）神经增强视频流系统，在本地客户端 iStreamPlayer 上进行算法改进与系统优化。核心目标：探索超越 BONES 的创新方向，提升视频流增强系统的 QoE、资源效率和增强能力。

---

## 二、已完成的工作

### 阶段1：环境搭建与基线确认

- 梳理目录结构，清理根目录冗余 Python 文件，重建 Git 仓库
- 读懂 iStreamPlayer 全链路（下载→解码→增强→渲染→分析）
- 确认三种渲染模式（OpenGL/EGL/Headless），选择 OpenGL + 注释帧输出做无头实验
- 跑通 BONES 基线实验（~12分钟/次，stable3g 轨迹）
- **基线结果**：avg_vmaf=66.47, QOE=57.96, stall_dur=22.22s

### 阶段2：内容感知调度初探

| 方法 | 结果 | 结论 |
|------|------|------|
| CA-BONES base_known | QoE -1.58, stall 90s | 静态延迟表低估高级别延迟→stall暴增 |
| EWMA 实测延迟反馈 | QoE 差距从 -4.15 缩小到 -1.58 | 部分有效，实测延迟比静态表准确 |
| per-seg KNN 延迟预测 | QoE -2.81 | KNN冷启动期预测不准→stall |

### 阶段3：VMAF 增益预测模型

- 训练 RandomForest 模型（R²=0.909, RMSE=3.11），12维特征
- 仿真器验证：所有 CA 模式 QoE 均低于 BONES
- 真实播放器 predicted 模式：QoE -6.92，预测VMAF导致过度自信→极端选择→振荡
- **关键结论**：不准确的预测比没有预测更有害；仿真器不是验证内容感知的正确场所

### 阶段4：CARES 资源效率方向

- 核心思想：不在质量奖励上做内容感知（导致振荡），而在**资源惩罚**上做内容感知
- λ_max=0.003：QoE 仅降1.5%，GPU能耗降18.8%，资源效率(VMAF/kJ)+21.9%
- **成功**：以极小的QoE代价换取显著的资源效率提升

### 阶段5：根因分析

- **内容感知QoE低于BONES的根因**：内容感知增加决策方差→相邻段质量差异大→oscillation暴增→QoE下降
- **结构性问题**：内容感知天然增加振荡，BONES全局平均更保守稳定
- fast_complete 是 BONES 默认配置，不是我们独有

### 阶段6：VMAF 平滑机制

- 级别切换惩罚（α=2.0）：**失败**，oscillation反而升到12.06（同一级别VMAF差异大）
- VMAF差值切换惩罚（α=0.3）：**成功**，oscillation从8.50降到7.60，QoE+2.18
- **教训**：必须直接惩罚VMAF差值，而非级别差值

### 阶段7：CARES + VMAF 平滑组合

| 指标 | BONES | 组合(均值) | 变化 |
|------|-------|-----------|------|
| avg_vmaf | 66.47 | 67.80 | **+2.0%** |
| QOE | 57.96 | 63.97 | **+10.4%** |
| oscillation | 8.50 | 3.79 | **-55.4%** |
| GPU能耗 | 31.34kJ | 25.48kJ | **-18.7%** |

- 发现**路径依赖/双稳态**：两次实验level分布完全不同，但QoE都高
- 原因：VMAF平滑惩罚鼓励"惯性"，初始段微小差异决定路径

### 阶段8：多段前瞻规划（Lookahead / MPC）

- 实现 N=2 滚动时域优化，O((num_br×num_lvl)^N)=400种组合
- **关键修复**：dl_time 单位 bug（bytes误当Kb，下载时间高估125倍）
- 多轨迹验证：6轨迹中4胜2负（3G_stable/3G_var1/4G_bus/4G_bicycle胜，4G_car/hd_fixed略输）

### 阶段9：多任务增强（当前阶段）

#### 9.1 系统实现

- **MultiTaskEnhancer**（`player/istream_player/modules/enhancer/enhancer_multitask.py`）
  - 扩展 IMDNEnhancer，支持5种任务组合：none/sr/sr_deblur/deblur/sr_deblur_fi
  - NAFNet-Small 去模糊模型（2.68M params, FP16, 7.7MB显存）
  - 去模糊在输入分辨率运行（240p~16ms, 1080p~31ms），先去模糊再超分
- **MTBONESController**（`player/istream_player/modules/nes/mt_bones.py`）
  - 资源感知GPU状态追踪 + 内容感知任务选择
  - Lyapunov优化选(码率,任务组合)对

#### 9.2 1080p非超分增强

- **突破**：BONES假设scale=1（1080p）不需要增强，直接abort
- **方案**：将1080p加入`deblur_only_set`，允许combo 3（deblur-only）通过
- SR组合对1080p标记为无效延迟(1e6)，控制器自然回避
- **意义**：突破"最高码率不增强"限制，1080p仍可通过去模糊提升感知质量

#### 9.3 关键发现

- hd_fs轨迹平均带宽15.7Mbps（范围1.2-28Mbps），足够直接下载1080p
- 多任务增强的价值在**中等带宽(1-5Mbps)**轨迹中更明显
- 当前VMAF质量表缺少deblur增益数据，控制器倾向于选none

## 三、我们做了什么 vs 原有BONES

| 维度 | 原有BONES | 我们的改进 |
|------|----------|-----------|
| 增强类型 | 仅SR超分 | SR+去模糊+（待实现插帧）多任务组合 |
| 最高码率增强 | 不增强（scale=1 abort） | 1080p支持deblur-only非超分增强 |
| 资源感知 | 无 | CARES内容感知资源惩罚 + GPU状态追踪 |
| 质量平滑 | 无 | VMAF差值切换惩罚（oscillation -55%） |
| 决策视野 | 单段贪心 | N=2多段前瞻规划（6轨迹4胜2负） |
| 延迟反馈 | 静态延迟表 | EWMA实测延迟反馈 + per-seg KNN预测 |
| 组合效果 | - | CARES+VMAF平滑：QoE+10.4%, 能耗-18.7% |

## 四、失败的方法与教训

| 方法 | 失败原因 | 教训 |
|------|---------|------|
| CA-BONES base_known | 静态延迟表低估高级别延迟→stall | 延迟必须实测，不能用静态表 |
| CA-BONES predicted | 预测VMAF导致过度自信→振荡 | 不准确的预测比没有预测更有害 |
| per-seg KNN延迟预测 | 冷启动期预测不准→stall | 冷启动是per-seg预测的硬伤 |
| 级别切换惩罚(α=2.0) | 同一级别VMAF差异大，级别不变≠VMAF不变 | 必须直接惩罚VMAF差值 |
| CARES λ_max=0.01 | λ太大→过度保守→120段不增强 | 参数需要仔细调优 |

## 七、关键技术决策记录

1. **渲染模式**：OpenGL + 注释帧输出（无头跑实验，不渲染画面但保留完整管线）
2. **去模糊策略**：在输入分辨率做去模糊，再超分（避免高分辨率去模糊的高延迟）
3. **1080p增强**：仅允许deblur-only，不允许SR（SR对1080p无意义，除非目标是4K）
4. **仿真器定位**：用于快速验证算法逻辑，不用于验证内容感知自适应（无per-seg延迟变化）
5. **实验环境**：conda环境`sr`，CUDA支持，RTX 5080 GPU
